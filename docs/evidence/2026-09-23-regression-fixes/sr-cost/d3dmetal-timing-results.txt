Counter/fence ordering correction (SDK contract, 2026-09-23)

The temporary D3D transport emits the producer encoder's updateFence:fence afterEncoderStages:MTLStageDispatch, ends that encoder, writes counter base on the same MTL4 command buffer, then enters state->encode. The backend sets the scaler fence before counter base+1, writes base+1 immediately before encodeToCommandBuffer, and writes base+2 immediately after. The restored consumer compute encoder subsequently waits on the same fence at MTLStageDispatch; that order is unchanged.

SDK source and exact contract:
- /Applications/Xcode.app/Contents/Developer/Platforms/MacOSX.platform/Developer/SDKs/MacOSX27.0.sdk/System/Library/Frameworks/Metal.framework/Headers/MTL4CommandEncoder.h, lines 118-131: "This method encodes a command that updates a MTLFence instance after all previously-encoded commands in the current command encoder, corresponding to afterEncoderStages, complete."
- /Applications/Xcode.app/Contents/Developer/Platforms/MacOSX.platform/Developer/SDKs/MacOSX27.0.sdk/System/Library/Frameworks/Metal.framework/Headers/MTL4CommandBuffer.h, lines 162-165: "This method captures a timestamp after work prior to this command in the command buffer is complete. Work after this call may or may not have started."
- /Applications/Xcode.app/Contents/Developer/Platforms/MacOSX.platform/Developer/SDKs/MacOSX27.0.sdk/System/Library/Frameworks/MetalFX.framework/Headers/MTLFXTemporalScaler.h, lines 370-371 describes fence as optional synchronization for the app's untracked resources.

Therefore the pre-MetalFX counter follows producer Dispatch work and its fence update; it is not merely placed before a later MTLFX wait. Retract the earlier tentative claim that this interval may contain the upstream producer wait. The MTLFX call's own use of its optional untracked-resource fence remains grouped with the operation; the interval is not a kernel-only measurement. New timing output names this interval metalfx_fence_span_ms; archived rows retain the historical metalfx_gpu_ms key. No redundant producer-wait diagnostic is warranted, and production ordering is unchanged.

Follow-up runtime-matched observations

A standalone MTL4 run aligned FFX jitter and output-cap policy (cap requested but not reached) measured scaler p50/p90 1.0704/1.0855 ms and passed output validation at mean 0.449134. Its actual scaler class was `_M4FXTemporalScalingEffectBBR` on Apple M5 Pro device registry ID 4294968672.

One isolated same-D3DMetal run created a public empty-descriptor MTL4Compiler on the borrowed MPL device and used it for the feature; command buffers/resources/fence order were not changed. It passed output validation at mean 0.449135; measured-only scaler p50/p90 was 2.2108/2.4505 ms. The trace reports the same device ID, compiler class (`AGXG17XFamilyCompiler`, nil label and pipeline-data-set serializer), scaler class `_M4FXTemporalScalingEffectBBR`, active and descriptor dimensions, scale limits, feature flags, reactive mask, and jitter as the direct run. The older 3.0678 ms borrowed result was not a fresh same-instrumentation control; do not attribute the lower follow-up number to compiler replacement.

The trace did find different caller texture usage/storage: direct inputs Shared usage 0x3 and output Private usage 0x3; D3DMetal inputs Shared usage 0x11 and output Shared usage 0x17. Both paths require no input staging and use the same Private usage-0x7 output shadow. Public buffer/heap/parent/IOSurface backing metadata is being added to the next fresh borrowed trace before selecting a matched-resource variant. These caller texture differences remain concrete, untested variables.

In the public-default run, all 32 counter and feedback records were individually valid, but MTL4 feedback GPU interval p50 was 1.6305 ms while timestamped full SR span p50 was 2.2938 ms. Do not treat those intervals as identical or use feedback as a cross-check for that run.

Conclusion and next work

The aligned direct scaler and the public-default same-D3D scaler remain about 2.07x apart at p50 despite matching device, actual scaler class, format, geometry, cap behavior, temporal flags, jitter, and effective output. Caller texture usage/backing still differs, and the compiler effect is not isolated. No production SR optimization is justified by these measurements; keep production fence ordering unchanged.
